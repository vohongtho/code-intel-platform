# v1.0.8 Go-Live Checklist

## Release candidate

- [ ] PR #43 head commit matches the approved release candidate.
- [ ] Quality workflow passes for shared, core and web TypeScript builds.
- [ ] Test workflow passes the complete core test suite.
- [ ] Release Readiness passes package build, npm pack, CLI version, atomic analysis, index trust, dirty-tree detection, canonical graph equivalence, and security gates.
- [ ] Code Intel PR Impact and source snapshot workflows pass.
- [ ] `code-intel/core/package.json` and `package-lock.json` both report `1.0.8` for the core workspace.
- [ ] Regression coverage confirms an unchanged caller/importer/inheritor still connects to a changed target.
- [ ] Search fallback tests distinguish `VECTOR_INDEX_UNAVAILABLE` from `VECTOR_QUERY_FAILED`.

## Pre-deployment

1. Back up the existing `.code-intel` directory for at least one representative repository.
2. Record the currently deployed npm/package version and Git commit.
3. Confirm Node.js 22 or newer is installed.
4. Confirm sufficient disk space exists for the current generation plus a staging generation.
5. Run:

```bash
code-intel --version
code-intel index-status /path/to/repository
```

A `legacy` result is acceptable before the first v1.0.8 analysis. `missing` or `corrupt` results must be investigated before deployment.

## Deployment smoke test

```bash
code-intel analyze --force --skip-embeddings /path/to/smoke-repository
code-intel index-status /path/to/smoke-repository
code-intel search "known symbol" --json
code-intel change-context /path/to/smoke-repository --files src/known-file.ts --max-tokens 2000
```

Expected outcomes:

- `.code-intel/current.json` exists.
- `index-status` returns `state: "trusted"`, `trusted: true` and `fresh: true`.
- Search reports truthful requested and actual modes, with accurate vector fallback reason.
- Changed/deleted source triggers a correctness-first full graph rebuild; zero-change keeps the fast path.
- Change context stays within the requested token budget.
- The previous generation remains available for rollback.

## Rollback validation

Before production rollout, force one controlled analysis failure and verify that:

- `current.json` still references the previous generation;
- search and index-status continue to read the previous generation;
- incomplete `.staging-*` directories can be removed safely.

Rollback procedure:

1. Stop new analysis jobs.
2. Restore the previous package version.
3. Restore the backed-up `.code-intel` directory only if the live manifest or generation was manually altered.
4. Run `code-intel index-status` and one known-symbol search.

## Post-deployment

- [ ] Analyze one small, one medium and one embeddings-enabled repository.
- [ ] Verify forced and auto analysis return `state: "trusted"` with `trusted: true`.
- [ ] Verify zero-change uses the fast path and changed/deleted source uses a clean full rebuild.
- [ ] Verify calls, imports, extends/implements, clusters, and flows match a forced clean rebuild after changing a shared target.
- [ ] Verify `analyze --force /repo`, `analyze /repo --force` and option-before-path command forms.
- [ ] Verify HTTP `/health`, `/openapi.json`, `/api/v1/index-status` and `/api/v1/change-context` when the dedicated transport is deployed.
- [ ] Verify MCP `index_status` and `change_context` when the dedicated MCP transport is deployed.
- [ ] Monitor error logs, disk growth and generation cleanup during the initial rollout window.

## Go/No-Go rule

Go-live is approved only when every automated workflow on the same head commit is successful and all mandatory pre-deployment checks above are completed. Any failed atomic analysis, trust-state mismatch, package metadata mismatch, high/critical audit finding or rollback failure is a No-Go.
